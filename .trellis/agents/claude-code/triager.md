# How this Trellis workflow runs the skill

You triage ONE issue with the AWS CDK issue triage skill at `skills/cdk-triage/cdk-issue-triage/SKILL.md` in your working directory (it is listed under Data sources). Read the whole file before you start, then follow it, with these changes for this workflow. Where they conflict with the skill, these win.

1. The issue is on `alvazjor/aws-cdk`, a fork of `aws/aws-cdk` used for this demo. Read it there (`mcp__github__issue_read` with owner `alvazjor`, repo `aws-cdk`). Everything else the skill reads (duplicate search, code search, file contents, tags, releases, pull requests) targets `aws/aws-cdk` and `aws/aws-cdk-cli`, which are public. Source permalinks use `aws/aws-cdk` commit SHAs. Issues on the fork are copies of `aws/aws-cdk` issues, usually without saying so: an `aws/aws-cdk` issue with the same title and text is that original, the same report and not a duplicate. Leave it out of the duplicate analysis, and do not use its labels, comments or linked fixes as findings of your own. A `#N` in the issue is an `aws/aws-cdk` number: read it there, but never write it in your comment (see item 6). The comment from `trellis-poc` that says the triage has started is this workflow's automatic notice: it is not a maintainer response, leave it out of the analysis.
2. Your working directory is a checkout of the fork's `main` (the same code as `aws/aws-cdk` main). You may grep and read it with the shell as well as through the GitHub tools.
3. Single issue only: no subagents, no batch mode (TRIAGEALL does not apply).
4. Labels: you do not only recommend them, you SET them. Call `mcp__github__issue_write` exactly once, with exactly these arguments: `method: "update"`, `owner: "alvazjor"`, `repo: "aws-cdk"`, `issue_number` (the issue), `labels` (the COMPLETE label list the issue should have afterwards: its current labels, minus `needs-triage`, plus the classification, priority and module labels you recommend). Use only labels that exist on `aws/aws-cdk` (`mcp__github__list_label` or `mcp__github__get_label` if unsure). Classification labels: `bug`, `feature-request`, `documentation` (doc gap), `guidance` (question or working as intended). Priority: `p1` or `p2` per the rubric in 5.4. Module: `@aws-cdk/<module>` (for example `@aws-cdk/aws-lambda`), or `package/tools` for the CLI. Never set any other argument (no body, state, assignees, milestone, title). If no label change is warranted, do not call it.
5. The response: you do not only draft it, you POST it. Call `mcp__github__add_issue_comment` exactly once, with `owner: "alvazjor"`, `repo: "aws-cdk"`, `issue_number` (the issue) and `body` (the Proposed Response, the same text as your output `comment`). The skill's read-only rules ("never posted", "MUST NOT apply" labels) are replaced by this: both calls take effect on the issue at once and nobody reviews them first, so make them only once the report is final, the labels first and the comment last, just before you submit.
6. Nothing else writes. You MUST NOT close, assign, edit or write anything else. Every write goes to `alvazjor/aws-cdk` only, never to `aws/aws-cdk` or any other repository. The Proposed Response greets the issue author with an @mention, `Hi @<author>,` (the `author` input), so they are notified; it MUST NOT @mention anyone else, and MUST NOT reference any issue, pull request or discussion at all: no `#N` (on a fork GitHub links a bare `#N` to the upstream issue), no `owner/repo#N`, no issue, pull request or discussion URL, since each adds a mention on the referenced item. Describe related work in words instead. Links to repository pages, source files, commits and docs are fine. The report of Phase 5 goes in your output `report` (Markdown, all nine sections), not in a file.
7. The `agent-toolkit-for-aws` aws-cdk skill the skill relies on is on GitHub, not in your working directory: before Phase 1, read `skills/core-skills/aws-cdk/SKILL.md` from `aws/agent-toolkit-for-aws` (`mcp__github__get_file_contents`, owner `aws`, repo `agent-toolkit-for-aws`), and read the files under `skills/core-skills/aws-cdk/references/` that it links when a CDK-domain question needs them. The `cdk-mixins` skill is not available: for mixins use the repository (`packages/@aws-cdk/cfn-property-mixins/` and the `aws-cdk-lib` sources) and the trusted docs.
8. Reproduction (Phase 4): synth level only, and only when it is quick. In a folder under `$TMPDIR`, run `npm init -y` and `npm install aws-cdk-lib@<version> constructs`, write a plain JavaScript app that builds the stack and calls `app.synth()`, run it with `node`, and inspect `cdk.out`. No deploy, no AWS calls, no `cdk init`. If it does not work within about five minutes, record "Not attempted" with the reason and go on.
9. Fill every output field and submit with `submit_output`.
